# RocketSMS

Мессенджер с сервером на **ESP32-C3** и Android-клиентом **RocketSMS** (**Android 11+**).
Серверная часть и бинарный протокол по-прежнему называются Pajer — это имя не влияет
на отображаемое название приложения и не ломает совместимость прошивки с клиентами.
Основной доступ из интернета — через публичный MQTT-брокер: ESP32 сам устанавливает
исходящее соединение, поэтому телефону не нужен входящий доступ к дому. Прямой TCP
по DDNS остаётся запасным вариантом для локальной сети и «домашнего» интернета.

## Железо

Подключённая плата (COM9, USB Serial/JTAG, VID `303A`:`PID 1001`):

- ESP32-C3 (QFN32, rev v0.4)
- **RISC-V RV32IMC**, 1 ядро, 160 МГц
- Wi-Fi 2.4 ГГц + BLE 5
- 4 МБ встроенной flash, ~400 КБ SRAM, PSRAM нет
- MAC `1c:db:d4:e1:0c:98`

Ассемблер здесь нецелесообразен: Wi-Fi стек — готовый бинарник Espressif, а узкое место — RAM и сеть. Сервер написан на C (ESP-IDF) с `-Os`, без JSON/TLS/аллокаций в цикле. Полную историю сервер не хранит: он пересылает кадр получателям и сразу забывает его, история живёт в приватном файле Android-клиента. Исключение — короткая очередь невручённых личных сообщений (до 16), которая удаляется сразу после доставки.

## Решения

| Параметр | Значение |
|---|---|
| Среда ESP32 | PlatformIO + ESP-IDF |
| Wi-Fi | STA (`DevideByZer0`) |
| Транспорт | Raw TCP, бинарный протокол, порт **1234**; MQTT 3.1.1, порт **1883** |
| Клиент | Kotlin, Android SDK 34, `minSdk 30`, без внешних зависимостей |
| Выход в интернет | MQTT `broker.emqx.io:1883` (основной); DDNS `zerozero.myddns.me:443` (резерв) |
| Индикатор | RGB LED (GPIO8): зелёный 2 с вкл / 2 с выкл без клиентов; синий при клиентах — 0.5 с полный цикл на 1 клиента, −50 мс за каждого следующего (мин. 0.15 с на 8); выкл при сбое |

Схема доступа:

```text
Основная:  Android → broker.emqx.io:1883 ← ESP32-C3 (исходящее соединение)
Резерв:    Android → интернет → роутер (port forward) → ESP32-C3:1234
```

MQTT-топики: `pajer/pajer-zero/up/<tag>` (клиент → сервер) и
`pajer/pajer-zero/down/<tag>` (сервер → клиент). Кадр бинарного протокола
передаётся внутри payload без изменений; `<tag>` — случайный идентификатор сессии.

## Сборка и прошивка ESP32

```powershell
cd D:\AIProjects\Pajer
$env:PLATFORMIO_CORE_DIR = 'D:\pio-core'
$env:TEMP = $env:TMP = 'D:\pio-temp'
$pio = 'C:\Users\abrig\AppData\Local\Programs\Python\Python312\Scripts\pio.exe'

& $pio run -e esp32-c3               # сборка
```

Переменные нужны, потому что кэш PlatformIO и temp перенесены на `D:` (на `C:` не хватало места).

`version.properties` и генерирует `include/fw_version.h`. В UART-логе при старте видна
строка `Pajer server vX.Y.Z (build N), chip=...`.

В логе появится строка `Got IP: ...`. Текущий IP платы — **192.168.0.107**, порт **1234**. Его нужно закрепить в DHCP-резервации роутера, чтобы адрес не менялся.

### Версионирование

Общие счётчики клиента и сервера хранятся в `D:\AIProjects\Pajer\version.properties`.
Перед сборкой APK Gradle увеличивает `client.code` и записывает `client.name = 1.0.<code>`;
перед сборкой прошивки PlatformIO увеличивает `server.code` и `server.name`.
Таким образом каждый новый APK имеет более высокий `versionCode`, чем предыдущий,
а версия прошивки видна в UART-логе. Текущая версия клиента отображается в
`Настройки`; нажатие на неё запускает проверку обновления. После текущего этапа
прошивка — **v1.0.15 (build 15)**, клиент — **v1.0.19 (build 19)**;
APK лежит в корне проекта как `RocketSMS-v1.0.19.apk`.

### Обновление клиента

APK **не хранится на ESP32** и не передаётся через MQTT. Используется только HTTPS:

1. Приложение раз в 6 часов читает `update.json` с
   `https://raw.githubusercontent.com/DevideByZer0/RocketSMS/main/update.json`
   (запасной URL — `https://github.com/DevideByZer0/RocketSMS/raw/main/update.json`).
2. Если `versionCode` в манифесте больше текущего — показывается диалог
   «Обновление» с текстом из `notes` и кнопкой «Скачать».
3. APK скачивается с GitHub Releases или raw-зеркала в `filesDir/update.apk`,
   проверяется **SHA-256** из манифеста и `versionCode` через `PackageManager`.
4. После подтверждения «Установить» приложение открывает системный установщик
   через собственный `UpdateFileProvider`. При выключенной установке unknown apps
   открываются системные настройки `ACTION_MANAGE_UNKNOWN_APP_SOURCES`.

Публикация нового релиза (после `gh auth login` и `gh auth refresh -h github.com -s repo`):

```powershell
python tools/publish_release.py --configure   # один раз: создать репозиторий, записать URL
cd android
.\gradlew.bat assembleRelease                 # сам соберёт APK и сразу выложит его на GitHub
```

`assembleRelease` после копирования APK в корень автоматически запускает
`tools/publish_release.py`: считает SHA-256, пишет локальный `update.json`, загружает
APK в репозиторий, обновляет манифест и создаёт/обновляет тег `v1.0.N`.
Подробности для релиза лежат в `release_notes.txt` (заголовок с версией скрипт добавит сам).
Запуск вручную тоже возможен: `python tools/publish_release.py`.

Иконка приложения — адаптивный launcher icon (`res/mipmap-anydpi-v26/ic_launcher.xml`,
слои `drawable/ic_launcher_background.xml` и `ic_launcher_foreground.xml`):
хромированная ракета с SMS-баблом на фоне неонового заката и перспективной сетки
в стиле фантастики 80-х. Исходники: `rocketsms-icon.svg` и `rocketsms-icon.png` в корне.

На Redmi/MIUI для установки через adb нужно включить:
**Настройки → Для разработчиков → Установка через USB / отладка по Wi-Fi** (иногда требует входа в Mi-аккаунт).
Иначе `adb install` падает с `INSTALL_FAILED_USER_RESTRICTED`.

## Вход, профиль и настройки

При запуске показывается сплэш, затем — отдельный экран входа с карточкой,
полями логина/пароля и списком аккаунтов на этом устройстве. Регистрация вынесена
на собственный экран (`Создать аккаунт` → имя, логин, пароль, подтверждение и
галочка скрытия логина). Аккаунты живут **только на устройстве**: логин,
отображаемое имя и сольный PBKDF2-HMAC-SHA256 хэш пароля лежат в
`filesDir/accounts.dat`. Пароль по сети не передаётся ни в TCP, ни в MQTT.
На одном телефоне можно завести несколько аккаунтов и переключаться между ними.
После успешного входа выбранный аккаунт сохраняется: фоновая служба сможет
подключиться даже после перезапуска процесса. Отображаемое имя — UTF-8 до 24 байт,
поэтому работает кириллица и любой язык.

В настройках (`⋮`) есть блок `Профиль`:

- аватар (16 готовых вариантов или своё фото из галереи);
- `Отображаемое имя` — виден всем в списке контактов и при поиске;
- `Логин` — виден только вам; галочка `Скрывать логин от всех` заставляет сервер
  рассылать другим клиентам пустой логин и выставленный флаг;
- `Сохранить профиль` и `Выйти из аккаунта`.

Ручного выбора сервера больше нет. Клиент сам перебирает кандидатов
(`ESP32 · LAN` → `MQTT · облако` → `DDNS`), запоминает последний работавший и сам
переподключается при потере связи. В шапке списка чатов и в настройках показывается
только маленькая точка состояния:

- зелёная — сервер в локальной сети;
- зелёная с синей обводкой — сервер в интернете (MQTT/DDNS);
- красная — соединения нет.

Экран настроек прокручивается, поэтому управление комнатами доступно даже на
устройствах с невысоким экраном.

### Поиск пользователя по имени

На вкладке `КОНТАКТЫ` поле поиска запрашивает сервер (`SEARCH_USER`) по мере ввода
(от 2 символов). ESP32 хранит в NVS каталог до 32 пар **логин → отображаемое имя**
и ищет подстроку без учёта регистра (ключ в нижнем регистре присылает клиент,
поэтому кириллица работает без Unicode-библиотек на микроконтроллере). В ответе
`SEARCH_RESULT` приходят только имя, стабильный `ref`, признак «в сети» — логин
никогда не попадает в результаты поиска, даже если он не скрыт. `ref` — это номер
слота каталога со старшим битом, **не логин**; он используется как ключ чата и
адрес получателя, поэтому переписка не рвётся при переподключении с новым `client id`.
В NVS пишутся только имена и логины, пароля нет.

### Сообщения пользователю, который не в сети

Личный чат теперь открывается и по офлайн-результату поиска. Если получатель не
подключён, ESP32 кладёт сообщение в небольшую очередь NVS (**до 16 записей**) и
сразу после его входа отправляет кадр `MSG_OFFLINE` с текстом и именем отправителя,
затем удаляет запись. Полная история по-прежнему живёт только на устройствах:
сервер не хранит переписку, а держит лишь невручённые сообщения до доставки.
При переполнении очереди клиент получает `ERROR 5`.

### Смайлики

Кнопка `☺` у поля ввода открывает набор из **24 готовых смайликов** (сетка 6×4).
Они заданы кодом в `MainActivity.kt`, не требуют внешних картинок и вставляются
в текст обычным Unicode — поэтому проходят через тот же бинарный протокол UTF-8.

### Приём сообщений без открытого приложения

После входа в аккаунт стартует `MessengerService` — foreground-сервис, который
держит TCP/MQTT-соединение и после `WELCOME` продолжает принимать кадры, даже
если `MainActivity` закрыта или экран выключен (удерживается частичный wake lock).
Сервис показывает тихое уведомление «Приём сообщений активен»; входящие личные
сообщения дают **звуковое уведомление с текстом**, видимое на экране блокировки.
При открытии приложения накопленные уведомления о сообщениях убираются.
На Android 13+ при первом входе запрашивается разрешение `POST_NOTIFICATIONS`.

### Очередь исходящих при отсутствии связи

Каждое отправленное вами сообщение сначала пишется в `filesDir/pending.dat` и
сразу показывается пузырём в чате. Если сервер недоступен, кадр остаётся в очереди;
после следующего `WELCOME` `MessengerBackend` отправляет все накопленные сообщения
по порядку. Эхо `MSG` или кадр `QUEUED` удаляет запись и заменяет локальный пузырь
реальным сообщением с id сервера. Очередь переживает перезапуск приложения.

Для мобильного интернета клиент сам дойдёт до `broker.emqx.io:1883`: после
неудачи локального кандидата он автоматически перейдёт к MQTT. Входящие
подключения к дому не нужны: ESP32 сам подключается к брокеру и слушает топик
`pajer/pajer-zero/up/+`. Проверка: в логе ESP32 должно появиться `CONNACK connected=1`.

Резервный прямой доступ по DDNS описан в [docs/ddns.md](docs/ddns.md), но с мобильной
сети он часто не работает (оператор не пропускает SYN на домашний IP).

## Протокол (коротко)

Кадр: `magic(0xA5) | type | len:u16 LE | xor | payload`.
`xor` считается по `type`, байтам `len` и payload.

Клиент → сервер: `HELLO`, `SET_NICK`, `PING`, `AVATAR_ANNOUNCE`, `DM`, `ROOM_MSG`, `BCAST`, `JOIN`, `LEAVE`, `CREATE_ROOM`, `TYPING`, `READ`, `LIST_USERS`, `LIST_ROOMS`, `SEARCH_USER`, `HISTORY`, `FILE_OFFER`, `FILE_REPLY`, `FILE_CANCEL`.

Сервер → клиент: `WELCOME`, `USER_LIST`, `USER_LOGINS`, `USER_REFS`, `AVATAR_ANNOUNCE`, `SEARCH_RESULT`, `MSG`, `MSG_OFFLINE`, `QUEUED`, `ROOM_LIST`, `HIST_ITEM`, `TYPING`, `READ`, `PONG`, `ERROR`, `FILE_OFFER`, `FILE_REPLY`, `FILE_CANCEL`.

`HELLO` / `SET_NICK`: `[nick_len][nick][login_len][login][flags][key_len][key_lower]`.
Старые клиенты шлют только первые два поля — сервер определяет формат по длине кадра.
Флаг `0x01` означает «скрыть логин»: сервер знает логин, но рассылает `USER_LOGINS`
с пустым логином. `PJ_C_AVATAR_ANNOUNCE` несёт только версию и адрес P2P-источника.

Тело сообщения: `msg_id:u32 | from_id:u16 | scope:u8 | target:u16 | ts:u32 | read_mask:u8 | len:u16 | text`.
`SEARCH_RESULT`: `[count]{[ref:u16][name_len][name][online]}`, где `ref = 0x8000 | slot` каталога — это не логин. `USER_REFS`: `[count]{[id:u16][ref:u16]}`. `MSG_OFFLINE` — то же тело сообщения плюс `[name_len][sender_name]`; `QUEUED` — `[msg_id:u32][ref:u16]`. Получатель в `DM` может быть как `ref`, так и старый числовой `id`.

### Передача файлов мимо сервера

Сервер только «знакомит» клиентов: пересылает `FILE_OFFER` / `FILE_REPLY` / `FILE_CANCEL`
с IP-адресом и портом отправителя. Сами байты файла через ESP32 не идут:

- **в одном Wi‑Fi** получатель подключается напрямую к отправителю по TCP и качает
  куски по 1 КБ;
- **через интернет** отправитель публикует те же кадры в MQTT-топик
  `pajer/pajer-zero/p2p/<transfer_id>`; ESP32 этот топик не слушает.

Кнопка `+` в поле ввода доступна в личном чате; принятые файлы сохраняются в
`Download/RocketSMS`, ссылка «Открыть» появляется в пузыре сообщения.
Проверка P2P-кадров добавлена в `tools/selftest.py`.

Так же переносятся **аватары**: сервер получает `AVATAR_ANNOUNCE` с версией и адресом
P2P-источника и рассылает его как `PJ_S_AVATAR_ANNOUNCE`, но сами байты не видит.
16 встроенных аватаров кодируются двумя байтами и рисуются кодом; своё фото
сжимается в 256×256 JPEG. Аватар идёт напрямую по TCP в одном Wi‑Fi или MQTT-топитом
`pajer/pajer-zero/avatars/<id>` (на который ESP32 не подписан) через интернет.
Кэш чужих аватаров лежит только в `filesDir` телефона.

## Проверка

Полный автотест протокола из локальной сети:

```powershell
python tools/selftest.py 192.168.0.107 1234
```

Тот же тест через DDNS (лучше запускать вне дома):

```powershell
python tools/selftest.py zerozero.myddns.me 443
```

Проверяет `WELCOME` с версией прошивки, `PING/PONG`, списки пользователей/комнат, broadcast, личные сообщения, `TYPING`, `READ`, создание комнаты, сообщения в комнату, P2P-сигналинг, отсутствие полной истории на сервере и ошибку «нет такого пользователя». ## История и логи

- **Сервер:** полная история не сохраняется. Кадр получает ID, уходит получателям
  и удаляется из стека обработчика; вместо массива на 64 сообщения (~17 КБ RAM)
  остаётся только счётчик ID. `PJ_C_HISTORY` игнорируется. Исключение — до 16
  невручённых личных сообщений в NVS (`pajer_queue`): они хранятся только пока
  получатель не вошёл в сеть, затем удаляются. Логин в сеть не попадает.
- **Клиент:** все сообщения пишутся в `filesDir/messages.dat`, а неотправленные —
  дополнительно в `filesDir/pending.dat`. Оба файла переживают перезапуск приложения
  и перезагрузку ESP32. Отметки «прочитано» сохраняются там же. Если получатель
  был не в сети, ESP32 сам доставит сообщение при его входе; MQTT-брокер по-прежнему
  не хранит сообщения (QoS 0, без retain).
- **Логи:** сервер их на носитель не пишет, только в UART. При разработке
  `PJ_DEV_LOG=1` (по умолчанию в `include/app_log.h`); для рабочей прошивки
  достаточно поставить `0` — все вызовы логов приложения исчезают из образа.

## Ограничения первой версии

- до **8 клиентов** и **8 комнат** одновременно;
- текст сообщения до **256 байт UTF-8**;
- сервер не хранит историю: офлайн-доставки нет, история есть только на устройстве получателя;
- регистрация локальная (на устройстве), пароль не передаётся по сети; но TCP и MQTT идут в открытом виде, топики не защищены;
- публичный доступ зависит от доступности MQTT-брокера (или DDNS + port forward в резерве);
- только STA (при пустом SSID сервер всё равно стартует, но без сети).

## Что дальше

- простой токен доступа в `HELLO` для публичного режима;
- SoftAP fallback при недоступности Wi-Fi;
- подтверждение доставки/прочитано уже работает: клиент передаёт ID автора в `READ`,

- ассемблерные вставки RISC-V только для CRC/хэшей, если понадобится.
